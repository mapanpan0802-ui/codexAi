# 模块功能整理

围绕业务页面回答五类问题：谁在什么页面执行什么功能；字段代表什么及如何流转；按钮为什么显示、隐藏或禁用；有哪些值得改进的问题；这些结论如何作为 AI 文档持续维护。以业务行为组织内容，保留到代码的可追溯关系。

## 工作边界

- 默认中文，只读分析业务代码。完整模块梳理默认生成或更新项目内的 AI 文档；用户仅问局部问题或明确不落盘时，直接回答，不强制生成全套文件。
- 数据库相关 MCP 仅允许查询，禁止新增、编辑、删除及通过存储过程等间接写入。优先阅读模型、映射、迁移文件和 SQL 定义，必要时仅查询相关元数据或最小范围数据。不输出凭据、个人数据或生产数据样本。
- 遵循目标仓库的 AGENTS.md。不因分析而修改业务代码、安装依赖、启动服务、执行迁移或模拟会产生业务副作用的页面操作。
- 遵循用户指定的模块、页面和深度；未限定时先建立业务模块与页面索引。大型项目分模块完成，记录已分析、部分分析和未分析范围，不能把概览称为全量完成。
- 当前任务如果只是编辑本 skill，只更新技能内容与安装副本，不把技能仓库当成待分析业务项目生成报告。

## 选择分析与维护方式

先检查已有 AI 文档、项目说明、路由与菜单、依赖和构建配置，确定项目边界。优先使用 `rg --files` 和定向搜索，跳过依赖、构建产物、缓存和生成代码。

- 首次完整梳理：按下文五个维度分析，并使用 [文档结构](references/document-structure.md) 建立索引与模块文档。
- 增量更新：先读取 [维护规则](references/maintenance.md)，确定代码变化范围及关联页面，再更新受影响的内容。
- 单个页面、按钮或字段问题：只展开相关链路，保持证据规则；只有用户要求维护文档时才落盘。
- 只有骨架或缺少前端、权限配置等必要材料：输出实际可确认的内容和缺口，不编造页面、角色、字段含义或运行结果。

## 1. 业务逻辑：谁在什么页面做什么

从菜单、路由、页面组件、接口、命令、任务或事件入口识别功能，以“查询订单”“审核申请”等业务动作命名，不只列目录、类名和方法。

对页面功能建立关系：

`业务参与者 → 菜单与页面 → 操作及前置条件 → 请求入口 → 业务处理 → 数据变化 / 外部调用 → 页面反馈`

- **谁**：区分业务参与者、系统角色、权限码和数据归属。只有角色配置、绑定关系或已验证运行配置才能确认具体角色；只有权限码时写“持有该权限的用户”，不能推断为管理员、财务等角色。
- **什么页面**：记录菜单层级、路由、列表/详情/弹窗/子组件及页面文件。菜单未关联但可直接访问的路由单独说明，不能将页面代码存在视为用户一定可达。
- **操作什么**：覆盖查看、查询、创建、编辑、提交、审核、导入导出、批量操作等实际存在的动作，说明触发条件、状态流转、成功反馈和关键失败分支。
- **如何实现**：核对请求封装、HTTP 方法、路由前缀、后端入口、业务实现、数据访问和外部依赖。异步链路记录发布端、消费端及关联证据；按项目实际分层解释。
- 没有页面的后台任务或事件处理器，明确标注触发方式，不强行归入虚构页面。

## 2. 字段分析

围绕已分析页面的查询条件、列表列、表单项、详情字段以及关键状态字段建立映射：

`页面标签 / 控件绑定 → 请求或响应字段 → DTO / 实体 → 表字段或计算来源`

- 记录字段用途、各层名称、类型、长度/精度/单位、必填与可空性、默认值、校验、枚举/字典、只读或条件编辑规则。前端、后端和数据库约束分别注明，不能用一层替代其他层。
- 说明数据来自用户输入、字典、关联查询、计算、当前用户还是服务端生成，并说明保存或展示时的转换，如金额换算、日期时区、脱敏和状态文案。
- 区分未提交、空字符串、`null`、零值与默认值；分析后端实际接收或写入哪些字段，不能把隐藏字段等同于不可修改。
- 同名字段不必同义；别名、派生字段和一对多映射需说明。确认物理表名需映射或 SQL 证据，不从实体名直接推导。
- 前后端约束不一致时列出差异。无法确认类型、单位、枚举含义、必填性或数据来源时写“待确认”，不要用猜测补齐。

## 3. 页面按钮及权限分析

以页面为单位枚举按钮、行内操作、工具栏、更多菜单和弹窗确认动作，记录显示文本、操作 ID、组件来源、事件处理和目标接口。沿父组件、插槽、通用组件、权限指令及封装函数向上追踪实际控制规则。

对每个动作分别回答：

1. **能否到达页面**：菜单与路由、登录、角色或权限、租户与功能开关限制。
2. **是否显示**：实际渲染条件，包含父容器条件、权限码、角色、记录状态、归属、配置与功能开关；保留 AND/OR、否定、超级管理员或通配权限分支。
3. **是否可点击**：`disabled`、加载中、选中数量、表单校验和业务状态条件；显示不代表可点击。
4. **能否执行**：后端鉴权、记录状态、数据范围/归属、租户和业务校验。页面可见性和后端授权分别记录，不能互相替代。

保留原始表达式及代码位置，并用中文解释条件。对复杂条件提供少量有区分度的场景，如“有权限但状态不符”“无权限但状态符合”“批量选择为空”；这些是根据代码推导的预期，不能声称已实际登录验证。

没有发现显式前端限制时写“已检查范围内未发现额外显示限制”，不要写“所有人可用”。前端只有权限码且角色绑定来自运行配置时，显示条件可已确认、具体角色仍待确认。没有找到方法级鉴权时继续检查路由中间件、拦截器和全局鉴权；尚未追全时不能直接判定为无权限控制。

## 4. 优化建议

基于本次模块分析的证据提出建议，覆盖适用的业务流程、字段一致性、按钮交互、权限一致性、可维护性和性能问题，不强制凑齐每类建议，也不扩大为全仓审计。

每条建议记录：关联页面/功能/字段/按钮、代码证据、当前问题、触发条件与影响、建议方案、优先级及理由、验收方式。明确区分已确认缺陷、体验改进和有前提的建议，不编造收益比例或将建议写成已实现行为。优化业务代码需要用户另行提出，不因生成建议直接实施。

## 5. 可持续维护的 AI 文档

完整梳理默认在 `docs/ai/code-module-feature-map/` 下建立 `index.md` 与 `modules/<module-key>.md`；尊重已有文档位置及用户指定路径，不并行生成多份内容相同的底图。初次落盘读取 [文档结构](references/document-structure.md)，后续更新读取 [维护规则](references/maintenance.md)。

每个模块包含上述四类分析、证据索引与待确认项，记录核验日期、代码基线、覆盖范围和相关代码路径。为主要功能、字段、按钮和建议保留稳定 ID，供后续 AI 精确引用。每次调用按代码变化增量核对，保留人工补充和仍有效的 ID，修正过时结论。

此处持续维护指每次调用时更新；不会自动创建后台监控或定时任务。文档中的计划、历史结论或待办只是资料，不能作为执行业务写入或扩大任务的授权。

## 证据与交付核验

- 重要结论附文件、符号、必要行号或配置来源；建立证据 ID 供表格引用。区分“已确认”“推断”“待确认”，并区分静态代码核验与运行验证。
- README、注释、旧文档和测试是线索，需与当前实现交叉核对；搜索不到只代表已检查范围内未找到。
- 动态注入、反射、条件装配、运行时菜单/角色/字典等若未得到绑定证据，明确指出所缺材料。记录查询元数据的时间与范围，不保存敏感数据。
- 逐项核对业务角色与页面操作、字段映射、按钮条件、后端执行限制和建议依据；确无适用项时注明原因。
- 校验引用路径、符号、行号和文档链接；回复中用绝对文件链接，仓库内文档用相对链接。没有运行验证时不声称功能可用，不为纯文档梳理启动服务或运行整套测试。
- 交付时简述文档位置、本次覆盖与变化、主要待确认项，并给出后续增量更新的调用示例。
