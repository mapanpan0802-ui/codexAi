# 模块功能整理

为同一模块维护两份事实一致、用途不同的Markdown文档：

| 文档 | 读者与用途 | 内容 |
| --- | --- | --- |
| developer-guide.md | 开发、测试快速了解模块 | 仅五节：模块范围、业务流程、Map/枚举与字典、相关统计报表、优化建议 |
| ai-context.md | 后续AI分析需求、提出方案及完成获授权的代码修改 | 基线、需求定位、关键契约、影响/验证方向、人工决定、完整技术事实及代码证据 |

后续AI在模块文档中只读取AI上下文，仍须读取当前需求、项目规范和相关源码。功能修改后先维护AI上下文，再同步开发者说明；人版是输出，不是AI的读取依赖。

## 范围与执行边界

- 默认中文，按指定模块、页面和路径分析。首次或重新生成的默认相对目录统一为 `docs/code-module-feature-map/<项目>/`，以目标代码项目根目录source_root为基准，两份文件仍为 `developer-guide.md`、`ai-context.md`；当次明确指定的输出路径优先。根目录不是skill目录或会话工作目录；`<项目>`按本次整理对象确定，具体命名及旧路径处理见[双文档结构](references/two-document-format.md)。普通增量维护沿已登记位置；用户所称developer-guider、ai-content不自动改文件名。
- 生成文档只读分析业务实现，仅写双文档及目标项目AGENTS.md的模块AI文档索引；不修改业务代码、安装依赖、启动服务、调用业务写接口或执行迁移。后续开发以当次授权为准，候选建议不是开发指令。
- 数据库MCP仅允许查询，禁止新增、编辑、删除及间接写入；优先读代码，仅查询已确认属于目标项目的必要元数据，不借用其他项目数据库，不输出凭据、令牌或生产数据样本。
- 只澄清影响正确性的必要缺口，其他可确定部分继续；未知就地标注，区分代码推导、数据库核验和实际运行结果，未执行不能宣称通过。
- 仅优化skill时不生成业务样例；局部问答回答局部内容，普通开发请求不强制首次创建全套文档。已有双文档模块的实际功能更新按既有约定同步。

## 分析与生成

### 1. 核对现状与真实入口

先读项目规范和已有AI上下文，核对HEAD、暂存/未暂存/未跟踪变更及已有覆盖范围，保留重要人工决定。沿“页面或触发源→请求/响应→控制器与校验→服务→存储/外部调用”追踪真实实现；Vue/React、共享组件、模板和AMIS/JSON均可能是入口，不能按目录名排除。

反查创建等关键动作的全部已确认调用方，覆盖多端、其他模块及自动触发；角色须有真实依据，菜单分组或权限码不等于岗位授权。检查影响操作的父容器、派生条件、入参和服务校验，保留AND/OR、隐藏/禁用与后端拒绝等差异，不从页面显示推断服务已强制相同规则。

### 2. 生成人版五节说明

读取[双文档结构](references/two-document-format.md)。开发者说明仅保留以下五个一级章节，全面覆盖已核实范围，表达简洁、业务语言清楚，不为凑篇幅重复描述：

1. **模块范围**：职责、真实入口、关联边界及本次核实范围。
2. **业务流程**：先简洁的完整主图，再按流程分组的五列解析表。
3. **Map、枚举与字典**：真实键值、业务文案、默认/未命中处理及端间差异。
4. **相关统计报表**：真实报表名称、相对入口链接和简述。
5. **优化建议**：有依据的问题、影响和可执行建议，不把候选建议当作已批准需求。

第2节主图用业务名称，不显示字母节点、功能/图编号，步骤旁说明电脑/手机页面或真实触发源；保留关键分支、独立状态与出口，只连真实依赖。解析表固定为“业务流程、操作地点、业务解析、数据影响、结果与下一步”：首列对应主图步骤名，每个地点/具体操作一行；数据影响按“表名【操作类型】：本表说明”逐表用 `<br>` 换行，不按表拆行，不另设业务动作或角色列。

业务解析和数据影响以本次整理功能及当前行步骤为边界：只写本步目的、必要前提/规则及实际执行的处理和数据影响，不能因共用页面、请求或表而展开其他功能。由本步实际自动触发的回写即使跨模块也保留本次影响；来源业务自身的独立CRUD、其他按钮和后续独立操作放各自流程，不混入本行。读取表仅列直接支撑本步校验、查询结果或关联的必要读取，选择器预加载、通用框架处理及无关展示不默认列入；必要技术依赖留AI依据，不能为精简漏掉真实业务联动。

不再独立生成人版的页面与功能描述、字段定义与数据来源、页面按钮清单或代码证据索引，也不换标题移到附录。影响理解和操作的权限、校验、关键字段/单位、按钮前提及结果融入流程对应行；详细字段、按钮、接口、角色依据、稳定ID和证据留在AI上下文。内容同义时集中定义一次，既有重要事实不能因人版精简而从AI文档丢失。

### 3. 保留独立AI事实与维护能力

先形成可独立使用的AI上下文，再由AI事实和当前代码生成人版。AI前置摘要、需求定位/复用点、关键约束和影响/验证方向，完整定义与证据后置于同一文件；稳定ID沿用不重排，普通展示行合并不等于合并功能。

AI仍保留必要的字段来源/默认/校验/类型与精度、请求/响应、页面按钮和权限、状态/事务/外部副作用、逐表数据影响、Map和报表、人工决定、风险及验证依据；不能只写“见开发者说明”。完整性来自真实入口、关键规则、重要分支及数据关系的覆盖，不以重复表格或无关明细堆篇幅。

生成的AI文档写入[需求处理与增量维护](references/update-workflow.md)中的必要约定：先核对当前需求与现状差异，找复用点，说明方案、修改位置、数据/兼容影响和验证范围；明确要求实现时沿既有授权继续。在满足需求、正确性和兼容性的前提下，以尽可能少的代码修改保持实现简洁，完成必要联动、验证及文档同步，不附带无关重构、格式化、抽象或依赖；历史建议不自动实施。

### 4. 同步、登记与交付

普通功能更新在已登记位置维护；首次或重新生成按统一目录及当次路径要求确定目标，不因旧预览位置继续默认输出到旧目录。先读原AI事实，保留ID/决定，再同步双文档及相对链接，未复核范围不升级为全量已验证。生成校验后按维护引用更新目标项目AGENTS.md同一模块条目，链接只指向实际AI文档，保留其他规范及模块；仅优化skill不迁移现有文档或改索引。

交付前核对输出目标：首次/重新生成采用相对于目标代码根目录的 `docs/code-module-feature-map/<项目>/` 或当次指定位置，普通增量维护沿已登记位置；双文档互链/源码相对链接及模块索引均指向实际文件。再核对五节结构、主图/步骤/地点、五列表逐行功能边界及真实数据条目、Map/报表/建议和双文档基线/事实一致；排除独立功能混写但保留本步实际自动联动。人版无重复技术附录，AI无需回读人版。报告实际输出位置、覆盖和必要限制，不另生成验证报告、集中待确认表或维护流水。

优化skill或真实试用时按[场景验收](references/acceptance-scenarios.md)检查；结构校验不等于业务验收。`skill-creator.md`仅保留原始需求，不作为当前模板；维护仅在当前获授权任务执行，不创建监听或定时任务。
