# 模块功能整理

为同一模块维护两份用途不同、事实一致的 Markdown 文档：

| 文档 | 读者与用途 | 内容重点 |
| --- | --- | --- |
| 开发者说明 | 开发、测试快速了解当前模块 | 业务流程与操作链接、按页面列举功能/规则/触发结果、字段/Map、按钮条件及报表 |
| AI 上下文 | 后续 AI 分析新需求、提出方案、完成获授权的代码修改 | 需求定位、可复用实现、关键契约与约束、修改影响、验证方向和独立事实依据 |

后续 AI 在模块文档中只读取 AI 上下文，仍须读取当前需求、项目规范及有关源码。完成功能修改后，先维护 AI 上下文，再依据当前实现同步开发者说明；开发者说明是输出，不是 AI 的读取依赖。

## 范围与执行边界

- 默认中文，按用户指定模块、页面和路径分析；没有明确页面时从菜单、路由及实现定位入口。只澄清影响范围或正确性的关键缺口，其余可独立工作继续。
- 生成文档时只读分析，不修改业务代码、安装依赖、启动服务、调用业务写入接口或执行迁移。后续使用 AI 文档开发时，代码修改以当次用户授权为准；候选建议和历史待办不是开发指令。
- 数据库 MCP 仅允许查询，禁止新增、编辑、删除及间接写入。优先读代码，必要时仅查询已确认属于目标项目的相关元数据；没有正确连接就注明缺口，不借用其他项目数据库。
- 不输出凭据、令牌、个人信息或生产数据样本；区分代码推导、数据库核验及实际运行结果，未执行不能写成通过。
- 仅修改 skill 时不生成业务样例；局部问答回答局部内容。普通开发请求不强制首次创建全套文档，已有双文档模块的实际功能变更按既有同步约定维护。
- 沿用现有文件名和位置；无约定时使用 `docs/modules/<module-key>/developer-guide.md` 和 `ai-context.md`。用户所称 `developer-guider`、`ai-content` 分别指两类文档，不据此自动改名或创建平行副本。

## 分析与生成

### 1. 定位入口与代码基线

先读目标项目 AGENTS.md、已有 AI 上下文和代码结构，核对当前提交及工作区变化。标明已分析、未分析及待确认范围，不把单页样例写成全模块覆盖。Vue/React、模板、共享组件和 AMIS/JSON 配置均可是真实页面入口，不能按目录名机械排除 `public`。

追踪 `页面或触发源 → 请求/响应 → 控制器/校验 → 服务 → 模型/存储或外部调用`，记录真实路径和符号。技术分层按项目实际实现识别，不强制套用框架。

### 2. 整理流程、规则与字段

- 每个独立业务动作建立稳定功能 ID；创建/编辑、取消/删除等约束不同的动作分开。同功能多端复用同一 ID，操作端依据实际入口填写电脑、手机或电脑、手机。
- 开发者说明独立设置“2. 业务流程”和“3. 页面与功能描述”。业务流程表固定五列：功能名称、操作端、功能描述、操作链接、处理结果。第3节按实际页面及页面内操作顺序列举功能，表格固定三列：按钮名称、关键规则、触发结果；状态、输入、归属、财务联动及前后端差异写入相应操作。
- 流程图用 A、B、C、D 等字母，分支建议 A-B1-C1-D1；各图独立编号。五列流程表的功能名称保留 `F-xxx`，功能描述注明“图标识 / 节点”与图中对应；完整映射保留在 AI 文档及人版证据索引，不额外增加技术列。状态/判断节点不要求功能条目，独立辅助入口不虚构先后关系。
- 字段沿页面绑定、请求/响应、实体/表列或计算/关联来源追踪；区分存储字段、别名、派生值和本地状态。说明类型、单位、精度、必填/可空、默认、校验、编辑条件及转换，区分缺失、空串、null 和零值。
- Map 按项目实际含义识别：页面映射、枚举、字典或键值对象。展开实际键值及类型、文案、默认/未命中处理和使用端，核对写入方、搜索条件与前后端差异；数据库列清单不能代替 Map 分析，声明迁移不能冒充实际部署 DDL。

### 3. 核对按钮、报表和预期表现

按页面/区域列举实际按钮及等价操作，覆盖工具栏、行内、批量、弹窗提交和共享控件；自动加载归入流程，被注释按钮不算当前入口。打开表单与提交分别列举，同名不同对象的按钮分开。

说明功能、可用条件和不可用表现。核对父容器、共享组件、实际入参及后端派生标志，保留 AND/OR 与例外；区分隐藏、禁用、加载中、客户端校验和后端拒绝。权限码不等于实际角色授权，没发现局部限制不表示任意用户可用。业务流程表的“操作链接”优先填写用户可进入的页面路由或真实页面链接；没有页面的自动任务、外部回调或后台动作填写真实触发入口或代码链接并注明类型，不用 API 地址冒充页面入口。接口参数和完整技术链路放证据索引及 AI 文档。

在“页面与功能描述”的关键规则和触发结果中给出可观察的检查点：前置状态或输入 → 操作 → 页面表现 → 数据结果。区分确认的业务期望、当前实现和已知缺陷；未运行的检查点不写成测试通过。第6节继续说明按钮可用条件，避免重复第3节完整规则。

相关统计报表固定用“报表名称、报表链接、简述”三列。只列真实统计页、页签或专用报表文件；优先已确认页面/路由，没有运行地址就链接真实代码并标注入口。普通列表、单项计算和通用导出不充作独立报表，不编造域名，不以 API/下载接口冒充页面，不展开逐指标财务公式。

### 4. 先形成独立 AI 上下文，再生成人版

读取 [双文档结构](references/two-document-format.md)。AI 文档前置摘要、需求定位、关键约束、影响及验证方向，完整事实表和证据后置在同一文件。所用 ID 均在本文件独立定义；同一规则保留一处完整定义，摘要只强调影响决策的关键值和例外。保留重建人版所需事实及重要人工约定，不能仅写“见开发者文档”。

生成的 AI 文档须包含新需求使用流程：核对现状差异及复用点，说明建议方案、修改文件、数据/兼容影响和验证范围。只求方案时不改代码，明确要求实现时沿既有授权继续，不机械增加一次审批。具体约定见 [需求处理与增量维护](references/update-workflow.md)，必要内容写入 AI 文档，不要求后续 AI 能读取 skill 的引用文件。

开发者说明按固定九节组织，主表使用业务语言，代码技术细节集中到证据索引。流程、字段、按钮和测试预期必须能直接理解，编号不代替说明。两份文档共同记录真实基线、分析批次和覆盖范围，未知就地标注；不单列“谁在什么页面操作什么”矩阵，不输出独立验证报告、集中待确认表或维护流水。

### 5. 更新与交付

已有文档按 [需求处理与增量维护](references/update-workflow.md) 原位维护，保留稳定 ID 和 AI 文档中的人工决策，以实际代码修正旧结论。只核对部分就标明范围，不将全量内容升级为已验证。维护在当前调用或获授权的功能更新中执行，不创建监听或定时任务。

交付前检查流程表五列及操作链接、图表对应、按页面组织的三列功能表、操作端依据、Map 键值、按钮前后端差异、报表三列及链接、AI 独立可读和两份事实一致；开发测试应能判断主要操作的页面与数据结果。给出输出位置、本次覆盖及必要限制。

优化 skill 或做真实试用时使用 [场景验收](references/acceptance-scenarios.md)，结构校验不能代替使用表现。`skill-creator.md` 保留原始创建需求，不作为执行模板；业务验收继续结合实际试用和用户反馈。
