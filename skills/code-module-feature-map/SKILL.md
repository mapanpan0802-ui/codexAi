# 代码功能地图

把“项目有什么功能、由哪些模块实现、从哪里进入、如何调用、读写什么数据”整理成可定位的说明。以业务功能组织结果，目录结构用于辅助解释。

## 范围与约束

- 默认使用中文，只读分析代码。仅在用户要求时生成或更新文档；不因梳理功能而修改业务代码、安装依赖、启动服务或执行迁移。
- 数据库相关 MCP 仅允许查询，禁止新增、编辑、删除，以及通过存储过程或其他间接方式写入数据。优先从实体、模型、Mapper、迁移文件和 SQL 定义分析数据关系；确需数据库补充证据时，优先查询表结构，限制查询范围，避免返回业务敏感数据。
- 遵循目标仓库的 AGENTS.md。配置文件只提取配置项用途，不输出密码、令牌、连接凭据或个人数据。
- 尊重用户指定的模块、目录和深度。未限定范围时，先整理项目级功能概览，再展开主要业务；大型仓库按业务域分批深入，并说明已覆盖和未覆盖部分。

## 分析方法

### 确定项目边界

阅读说明文档、依赖清单、工作区和构建配置，识别技术栈、子项目、启动入口及模块边界。优先使用 `rg --files` 和定向搜索，跳过依赖目录、构建产物、缓存、压缩文件和生成代码；仅在相关功能依赖它们时进一步查看。

只有骨架、配置或空目录时，如实说明当前没有可识别的业务实现。不要把 IDE 配置、依赖声明或计划中的功能当作已经实现的能力。

### 建立功能清单

结合可执行代码中的路由、菜单、页面、控制器、命令、任务调度、事件处理器和消息消费者识别功能。README、注释和设计文档作为线索，与实际实现交叉核对。

以用户操作或业务动作命名功能，例如“订单查询”“库存扣减”，避免只罗列类名或把每个方法列成独立功能。区分业务模块、通用组件和基础设施；目录名相似不代表属于同一功能。

### 从入口追踪实现

对需要展开的功能，沿实际引用追踪：

`入口（页面 / API / 命令 / 任务 / 事件） → 核心业务实现 → 数据访问 / 外部依赖 → 返回结果或副作用`

按项目实际分层解释，不强制套用 Controller / Service / Mapper。前后端分离时，核对页面调用、请求封装、服务端路由及路由前缀；涉及异步处理时，注明发布端、消费端及其连接证据。

保留影响功能理解的分支：权限校验、状态流转、事务边界、缓存、租户隔离和外部服务调用。仅记录代码中能确认且与当前功能相关的行为，不额外开展全面审计。

接口声明不足以确认具体实现。遇到动态注入、反射、插件、条件装配或运行时配置，寻找注册与绑定证据；无法静态确认时，标注待确认点及所缺信息。区分“代码存在”“入口已关联”“运行时已验证”，没有运行证据时不声称功能可用。

### 记录代码证据

- 为主要功能提供入口与关键实现的文件路径、符号名，必要时附已核实的行号。接口注明方法和完整路径；任务或事件注明触发方式。
- 区分“已确认”“推断”“待确认”。业务名称可以是归纳，但实现行为必须有证据；推断需说明依据。
- 分别核对调用关系与数据关联。实体引用只能证明代码使用该实体；确认物理表名需查看映射配置或 SQL，确认写入行为需查看实际写入逻辑。
- 测试文件可辅助理解预期行为，但不能替代对实现的阅读。搜索不到时说明搜索范围，不将其等同于整个项目绝无此功能。
- 回复中的本地文件链接使用绝对路径；保存到文档的链接根据文档所在位置计算，便于仓库内跳转。不编造路径或行号。

## 输出方式

根据用户关注点调整详略，通常包含：

1. **项目概览**：技术栈、子项目、核心业务域及本次覆盖范围。
2. **功能地图**：使用表格列出业务模块、功能、入口、核心代码位置、主要数据或外部依赖、确认状态。字段无证据时填“待确认”或“不适用”。
3. **重点功能链路**：展开主要功能的调用顺序与关键规则，附可定位的代码证据；图示能帮助理解时使用简短 Mermaid。
4. **待确认项**：列出文档与实现不一致、缺失实现、动态关系和需要运行环境才能确定的问题，并给出核实方向。

用户只问某个功能的位置时，直接给出入口、核心实现和必要链路，不强制输出全项目报告。用户要求保存文档时遵循指定路径；未指定时可使用 `docs/code-module-feature-map.md`，先检查已有文档，避免覆盖无关内容。

交付前核对主要结论是否有代码证据、引用路径是否存在、行号是否有效，且结论没有超出已阅读范围。纯文档整理不为验证而启动服务或运行整套测试。
