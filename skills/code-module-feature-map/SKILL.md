# 模块功能整理

为同一业务模块交付两份相互关联的文档：开发者通过第一份理解当前业务、字段和页面操作；新 AI 通过第二份定位代码、掌握现状及约束，在用户明确提出后继续需求开发和版本迭代。

当前为按真实样例提炼的试用版。`skill-creator.md` 是保留的创建需求，不作为每次执行时的分析模板；其中待补充的验收标准和边界需根据用户反馈更新，不自行视为已经确认。

## 输入与范围

输入通常是项目路径或当前业务仓库、模块名称、可选页面/菜单路径与输出位置。

- 先读取目标项目的 AGENTS.md、现有模块文档及代码结构，再确认真实页面入口；收入、支出、箱罐等只是示例，不把本机项目路径或技术栈写成通用前提。
- 有明确页面时从页面进入；只有模块名时，通过菜单、路由和相关接口确定范围。存在多个不兼容实现且无法判断目标时，只澄清影响范围的关键信息，其余继续分析。
- 枚举发现的页面和动作，标记“已分析 / 未分析 / 待确认”。样例、局部分析和全量模块整理分别标明，不能把一个页面代表整个模块。
- 源码可能位于 Vue/React 组件、服务端模板、AMIS/JSON 等配置或共享组件。不能仅因目录名是 `public` 就忽略实际维护的页面源码。
- 分析已有实现；业务流程、字段含义、按钮功能与可用条件有证据才确认，没有材料时写明缺口。
- 当前仓库只有技能配置、用户只要求编辑技能或单纯修复业务缺陷时，不强行生成业务模块报告；没有业务源码则说明缺口。用户要求以其他仓库制作样例时，仅对明确选定的范围分析。

## 交付与执行边界

- 默认中文。完整模块整理生成或维护两份 Markdown；仅询问一个字段/按钮或用户明确不落盘时，回答局部问题即可。
- 遵循当前会话和目标项目约束。仅为整理文档，不修改业务代码、安装依赖、启动服务、调用写入接口或执行迁移。
- 数据库相关 MCP 仅允许查询，禁止新增、编辑、删除和间接写入。先读代码与映射，必要时仅查询目标库的相关元数据；目标连接不可用时注明，不使用其他项目的数据库冒充核验结果。
- 不输出凭据、令牌、个人数据或生产数据样本。静态推导、数据库结构核验、浏览器运行验证分开标注；没有执行就不能称为测试通过。
- 生成优化建议、AI 接手步骤或验证方案不授权实际实施。读取旧文档时，将现状、候选建议和已批准任务分开，不把历史待办当作新指令。

## 分析流程

### 1. 业务流程与实现链路

追踪 `功能及前置条件 → 接口 → 业务实现 → 数据变化或外部调用 → 返回结果与异常处理`。

说明查询、录入、编辑、审批等实际存在的动作，记录关键状态流转、失败条件和模块边界。没有页面的任务注明触发源。按代码实际分层定位，不强制套用某个框架。

完整模块整理先按独立业务动作建立功能清单和稳定功能 ID，再据此生成流程图与功能表。每个功能节点显式标注同一 ID（如 `F-001`），功能表列出对应的流程图与节点；两者的功能名称、前置条件、状态变化和结果一致。每条功能至少对应一处图中节点，每个功能节点都有表格条目；状态节点和判断节点单独标识。辅助功能可放入独立流程图，不为覆盖表格而虚构先后关系。具体格式见 [双文档结构](references/two-document-format.md)。

### 2. 字段与 Map

先识别项目中 Map 的具体用法：页面 `map/mapping`、后端 `typeMap`、枚举、字典，或真正的键值对象结构。不能只提供数据库列清单就声称完成 Map 分析。

- 字段链路：页面标签/绑定 → 请求/响应键 → DTO/服务字段 → 实体/表列或计算/关联来源。展示字段、别名和派生字段与实际表列分开。
- 对已纳入范围的 Map 展开实际键值、值类型、业务文案、默认/兜底键、未命中处理及引用页面。HTML 文案提取业务含义，样式有状态含义时另记。
- 对照前端 Map、后端枚举、搜索条件和写入方，记录缺失值、过时文案、同值异义及历史注释冲突。冲突并列列出来源，不用猜测统一口径。
- 记录字段来源、类型、单位、精度、必填/可空、默认、校验与编辑条件；前端、后端、数据库约束分别注明。未查实际库时不能把迁移或注释当作已部署 DDL。
- 对金额、日期和状态等关键字段说明转换、计算、单位和流转条件。区分缺失、空字符串、`null`、零值及默认值；隐藏或禁用的表单字段不等于后端不能修改。

### 3. 列举页面按钮：描述按钮功能与可用条件

按页面及区域列举实际存在的按钮，以及承担同类操作的菜单项、链接和上传控件。覆盖工具栏、行内操作、更多菜单、弹窗确认和批量操作；从调用点追踪共享组件、父容器与实际入参。页面自动加载等无按钮触发的行为归入业务流程。被注释的按钮和未实例化配置不作为当前可用按钮。

每个按钮记录稳定按钮 ID、页面/区域与文案、关联功能 ID、按钮功能、可用条件、不可用时的表现或原因，以及代码证据。按钮功能说明操作后发生什么、影响哪些数据或状态；可用条件用中文说明所需权限、记录状态、数据归属、选择数量、输入校验及其他实际前提。

- 区分隐藏、显示但禁用、加载中阻止重复点击、提交校验失败和后端业务拒绝，不把后端拒绝条件写成已经实现的前端禁用规则。没有显式限制时说明已检查范围与共同前提，不推断所有用户均可用。
- 可用条件保留实际 AND/OR、否定及例外分支。先核对父容器和共享组件条件；使用后端派生标志时展开其业务含义，再与实际执行校验对照。复杂条件可附原表达式或少量场景说明。
- 打开弹窗与确认提交分别描述；相同文案但作用对象不同的按钮分别列举。名称随状态切换的按钮，说明各分支功能及条件；同一业务功能的不同按钮通过功能 ID 关联流程图与功能表。
- 为确认按钮功能和条件，按需追踪回调、请求、路由及服务实现。主表不强制列出每个按钮的完整 URL、HTTP 方法和参数；需要辅助接手开发的接口细节放入 AI 上下文或证据说明。
- 权限码与实际角色授权分开核对；菜单种子不等于部署环境已授权，没有角色绑定证据时不推断具体角色。前后端规则不一致时说明各自行为和待确认项。

### 4. 相关统计报表

查找与当前模块有实际关联的统计页面、报表页签或报表文件，仅以“报表名称、报表链接、简述”三列列举。简述用一两句话说明统计内容和用途，必要时注明影响理解的关键范围或口径，不展开逐指标公式和整段财务口径分析。

报表链接优先使用已确认的报表页面地址或前端路由；没有可确认的运行地址时，提供真实报表代码文件链接并注明是代码入口。同一页面的报表页签注明进入方式，不编造域名，不以数据 API 或下载接口冒充报表页面链接。只列实际发现且与模块相关的报表，不把普通业务列表、单个计算字段或通用导出按钮当作独立统计报表。未发现时简要说明检查范围内未发现相关统计报表。

### 5. 面向下一次开发的上下文

第二份文档需提供新 AI 的阅读顺序、已核对的现状、关键代码入口、业务约束、共享依赖与修改影响、已知问题、后续开发所需验证方向和人工决策背景；持续更新的基线保存在文档元数据中。

依赖第一份文档已有字段/动作 ID 引用详细定义，保留影响开发决策的关键事实，避免复制整张字段表。明确区分“已实现”“候选建议”“用户已确认需求”；没有新需求时不虚构版本计划或代替用户实施优化。

## 输出与维护

首次落盘读取 [双文档结构](references/two-document-format.md)。同模块始终保留“开发者说明 + AI 接手上下文”两份交付，采用相同模块 ID、分析批次和覆盖范围，并互相链接。

生成的文档不单独输出“验证结果、待确认与维护”章节，也不附本轮集中验证报告、待确认表或维护流水记录。必要的不确定信息直接在对应业务、字段、按钮或报表条目中简短标注，避免将未知写成事实。代码核对、文档自检和增量维护仍作为技能内部流程执行。

优先原位维护目标项目已有的同类文档并遵循其命名规范。没有约定时使用 `docs/modules/<module-key>/developer-guide.md` 与 `ai-context.md`；两份文档可以位于不同目录，但相互链接必须可解析。用户指定位置时按指定位置交付。

后续更新读取 [增量更新流程](references/update-workflow.md)。核对代码基线、工作区及关联配置，只更新实际复核内容，保留人工补充与稳定 ID，修正过时结论，不重复生成平行文档。此维护在调用时执行，不创建后台监听或定时任务。

## 试用阶段自检

以下是执行自检，不替代用户尚未补充的正式验收标准：

- 两份文档职责清楚，新 AI 能从第二份找到入口和约束，再到第一份核对业务/Map/按钮证据。
- 当前范围内的关键功能可对应到真实入口；Map 包含实际键值；按钮功能、可用条件及不可用表现有代码证据，缺失信息明确标注。
- 统计报表使用“报表名称、报表链接、简述”三列，链接可定位且不是冒充页面的数据接口；简述与实现一致。
- 流程图与功能表中的功能 ID 集合一致，表格引用的图/节点存在；逐项核对名称、前置条件、状态与结果，图中分支和连线不超出代码证据。
- 两份文档基线与覆盖状态一致，链接有效，人工补充保留，静态分析没有被写成运行通过。
- 交付时给出文档位置和本次覆盖范围，不额外生成验证、待确认与维护章节。真实样例反馈到来后，仅针对已观察到的问题调整技能与验收标准。
