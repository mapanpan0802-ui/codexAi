# 增量维护规则

当用户要求更新已有模块文档，或完整梳理命中已有文档时读取。目标是让下一次 AI 能判断结论的范围、来源和时效，并直接定位需要复查的代码。

## 确认基线与变更范围

1. 阅读项目索引、目标模块文档和人工补充，检查各模块自己的最后核验基线；不要用索引最新时间代表所有模块都已核验。
2. 检查当前分支、HEAD、工作区状态、相关新文件与变更。仅执行只读 Git 操作，不切换分支、重置或清理用户改动。
3. 基线提交在本地可解析时，比较基线到 HEAD，并补充暂存、未暂存和相关未跟踪文件；只比较最后一次提交会漏掉变化。新文档本身的变动不视为业务代码变化。
4. 基线缺失、被改写或不在本地时，对目标模块重新扫描并说明，不能声称已经完成精确增量比较。非 Git 项目记录核验范围与文件指纹等可用依据。
5. 阅读上次记录的工作区状态。旧结论如来自未提交代码，仅凭提交号无法还原旧快照；使用已有路径与符号重核相关条目，不能把“HEAD 未变”解释为“实现未变”。

## 扩展影响范围

以变更文件为起点，查找引用和依赖，覆盖直接页面及受公共逻辑影响的模块：

- 菜单、路由、页面和请求封装变化：复查可达性、功能入口、按钮与接口对应关系。
- 权限指令、通用按钮、父容器、角色绑定、鉴权中间件变化：复查所有相关按钮的显示、禁用和执行限制。
- DTO、实体、字典、计算逻辑、SQL 和表映射变化：复查字段名称、约束、枚举、来源及展示。
- 服务逻辑、状态机、数据范围或外部调用变化：复查操作前置条件、状态迁移、副作用及既有建议。

相关的共享逻辑未改，不代表运行时角色、字典或功能开关未改。动态配置无法获取时保留时间和待确认状态。影响面不清时扩大目标模块的复查范围，不假定旧结论有效。

## 更新文档内容

- 按稳定 ID 更新已有条目，补充新增页面/字段/按钮；用户未指定全项目时只更新目标及必要关联部分。
- 实现被移除、重命名或迁移时核对新位置；确认移除后标记历史变化，不能只追加新条目而保留相冲突的旧结论。
- 同步字段、按钮、业务流程、建议和证据索引间的关联。旧建议已经修复时依据当前代码更新状态；仅看提交说明不足以认定修复。
- 保留人工补充、业务决策和不采纳理由。人工说明与当前实现冲突时并列记录差异，待确认内容不自动升级为事实。
- 只有实际重新检查过的模块或条目才更新“最后核验时间”和基线。只核验部分时标明本次覆盖；其他受影响部分设为“待重验”，不能整体刷新为“已分析”。
- 如果本次分析了工作区中的业务改动，记录 HEAD、未提交状态及相关路径；必要时保存相关文件的内容指纹，不将 HEAD 描述为完整分析快照。
- 对未受影响的文档不做格式重排或无意义重写，避免遮蔽真正的业务变化。

## 完成核验与交付

核对新增或变更条目的代码证据、路径和符号，校验模块索引与内容链接一致、引用 ID 可解析。静态分析仍保持静态核验标记；没有运行证据不能升级为运行验证。

交付说明本次更新的模块与文件、主要变化、未覆盖或待重验内容。后续可使用：

```text
使用 $code-module-feature-map 更新订单模块 AI 文档，核对自上次基线以来页面、字段和按钮权限的变化，保留人工补充。
```

文档不会自行监控仓库。只有后续调用此技能或用户另行授权的维护流程会触发更新，不自动创建计划任务、钩子或后台服务。
