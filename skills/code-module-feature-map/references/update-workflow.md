# 需求处理与增量维护

更新已有模块说明，或将生成的 AI 上下文用于后续新需求时读取。后续 AI 只把 AI 上下文作为模块文档输入，开发者说明是同步输出；本流程不授权额外业务开发。

## 核对输入与影响

- 读取当前需求、项目规范、AI 上下文及有关源码，取得基线、覆盖范围、稳定 ID、人工决策和两份输出路径，不要求读取旧开发者说明。
- 比较基线到当前 HEAD，并检查暂存、未暂存和相关新文件；提交号不能覆盖工作区内容，不切换分支、重置或清理用户改动。
- 基线不可解析或事实不足时，从代码及当前用户说明补齐；不回读人版形成依赖，不声称做了精确增量核验。动态角色/字典/配置不可得时就地保留未知。
- 按真实变更扩展到调用方、共享组件及依赖；公共 Map、请求封装、模型和金额计算需检查不同实参/入口的影响。

## 新需求的处理约定

生成时将以下必要约定写入 AI 文档，后续使用不依赖本引用文件：

1. **理解现状差异**：核对需求目标及当前实现，定位入口和调用链，识别已有可复用实现；文档与代码冲突时以复核后的实现修正文档。
2. **提出具体方案**：说明建议改法、关键理由、改动文件/符号、字段或接口契约变化，对历史数据、兼容、权限、状态及实际关联统计/导出的影响，以及验证范围。简单变更简述，不凑多方案。
3. **按请求执行**：仅要求方案时不改代码；明确要求实现时沿已有授权继续代码修改及适当验证，不机械增加一次批准。只对影响正确性的必要缺口澄清，其余可独立工作继续。历史候选建议不是新开发指令。
4. **记录真实结果**：区分已完成、未完成、失败、未验证和仍为方案的部分，不以改文档代替完成实现，不将建议用例写成通过。数据库 MCP 仅查询的约束贯穿整个过程。

## 功能更新后的双文档同步

1. 核对实际实现和影响范围，保留未实施建议及重要人工约定。
2. **先更新 AI 文档**：维护前部摘要/需求索引/关键契约，后部完整事实和证据；同一规则在本文件只保留一处完整定义。新增、拆分、移除时修复全部本地引用，不重排稳定 ID。
3. **再更新开发者说明**：从更新后的 AI 事实和当前代码生成九节人版，无须读取旧人版补背景。第2节业务流程表固定为功能名称、操作端、功能描述、操作链接、处理结果五列；第3节“页面与功能描述”按页面及操作顺序列举按钮名称、关键规则、触发结果三列。保留字段/Map、按钮条件、报表及可观察检查点，功能/图节点/页面按钮/证据映射集中到第9节。信息不足就先补齐 AI 文档，不能只写一份而宣称完成同步。
4. 两份输出使用一致的模块 ID、真实基线、本次批次及覆盖范围；实际功能更新后在本轮完成同步，不等待另一次重新生成请求。讨论方案未实施时不改写已实现状态，未复核内容不升级为全量已验证。

## 同步检查

- 功能变化同时更新流程字母节点/分支、五列功能表、真实操作链接、按页面组织的三列功能表及第9节映射；修复目录/章节引用，F/字段/按钮等稳定 ID 不随排版变化重编号。AI 文档保留页面顺序与功能归属，不要求读取旧人版还原布局。
- 字段和 Map 变化检查请求/响应、写入、校验、默认、派生展示及搜索；前后端差异和实际库缺口保留。
- 按钮变化检查父容器、派生标志、实际入参和服务执行条件；主表仍说明可用条件及不可用表现，完整技术细节留在 AI 文档和证据。
- 报表保持三列及真实入口，保留影响理解的范围；不将通用导出新增为统计报表，不扩展成逐指标财务公式分析。
- 验证场景体现前置状态/输入、操作、页面表现及数据结果；业务期望与实际缺陷分开，未执行不能宣称通过。

## 交付前自检

确认 AI 在没有开发者说明时仍能定位实现、解释规则、形成方案并确定影响/验证；人版可由开发测试直接理解。检查两份事实、基线、范围、ID及链接一致，图表对应有效，人工决策保留。

交付文档位置、本次同步范围及实际限制，不附集中验证报告、待确认表或维护流水。维护在当前调用或获授权的功能更新中执行，不创建后台监听或定时任务。
