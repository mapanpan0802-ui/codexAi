# 双文档增量更新流程

更新已有模块整理结果时读取。优先使用已有两份文档位置，保留人工补充、需求状态和稳定 ID。

## 基线与影响

- 读取两份文档的代码基线、核验范围和未确认项。基线不一致时先找出各自实际核验范围，不能直接把日期改成相同来掩盖差异。
- 只读检查当前提交、分支、暂存、未暂存和相关未跟踪文件；比较上次可解析基线到当前 HEAD，同时考虑工作区变更。不要切换分支、重置或清理用户改动。
- 基线不存在、无法解析，或旧结论来自无法还原的未提交内容时，重新核对相关模块，说明本次不是精确 Git 增量。
- 从变更扩展到受影响页面与共享依赖。公共 Map/列组件需检查所有实参不同的调用方；权限、字典、请求封装、实体和金额计算变化可能影响多个功能。
- 动态角色、字典、菜单与功能开关不一定反映在 Git 中；来源不可得时保留核验时间和缺口，不能声称配置未变。

## 同步两份文档

- 开发者文档更新受影响的业务、字段、Map、按钮功能与可用条件；AI 文档更新关键事实、代码地图、影响范围、验证方法与已确认的需求状态。
- 功能新增、变更、拆分、移除时，同步修改流程图节点/分支、功能表及其图/节点引用；保留原有稳定 ID，新增功能分配新 ID。拆分时说明原 ID 的保留对象，修正 AI 文档中的关联引用，不留下旧图与新表描述不同版本的情况。
- 新增条目分配新 ID；实现移除或迁移时核对新位置，修正旧事实，在相关条目中保留必要的原 ID 与变更原因。不能只追加新内容而留下冲突结论。
- 字段、Map 和权限变更要同时校对请求/响应、后端限制和页面显示；未重新核验的部分标记“待重验”。
- 按钮变更时同步核对用途、可用条件、不可用表现及关联功能 ID；保留按钮原 ID，不因文案或表格格式变化重新编号。按需检查请求及服务实现以核实行为，主表保持以按钮功能和可用条件为中心。
- 报表新增、迁移、移除或口径变化时，同步更新“报表名称、报表链接、简述”三列表；核对实际入口和模块关联，不扩展为逐指标统计与财务口径章节。
- 两份文档使用同一分析批次，范围与状态明确；只复核部分时记录本次具体范围，不把全部内容升级为最新或全量已完成。
- 对建议是否修复，以当前实现和实际验证证据判断。用户尚未确认的候选建议不得变成自动实施任务，人工“不采纳”理由保留。
- 不机械重写无关章节、不覆盖人工背景和决策；存在人工说明与实现冲突时保留差异及待确认状态。
- 按本次输出规范更新既有文档时，移除独立“验证结果、待确认与维护”章节；其中仍有用的事实、人工决策和缺口归入相应条目，必要基线归入元数据，不重新附集中报告或维护记录。

## 自检与交付

检查两份文档互相可达、代码路径/符号/必要行号有效、关联 ID 一致、核验基线与工作区描述准确。对照所有流程图中的功能 ID 与功能表 ID，检查集合一致、图/节点引用有效、同 ID 的名称/前置条件/状态变化/结果一致，辅助功能未被编造成主流程的必经步骤。未运行的测试保留“建议用例”状态。

核验结果供内部自检使用，交付给出两份文档位置与本次范围；缺口在相关条目中就地标注，不生成独立验证、待确认或维护章节。持续维护只在后续调用或用户另行授权的流程中执行，不自动创建定时任务、钩子或后台服务。
